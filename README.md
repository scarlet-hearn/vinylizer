## 固定图层数下的拟合改进

本轮改动保持输出图层数不变，继续使用游戏的 228 柔边椭圆：

- **修正渲染梯度**：前向在线性光空间混色，反向现在也经过相同的 sRGB 转换链；Alpha 梯度同时考虑上层和下层的透射率。完全不透明的图层不再通过 `log(0)` 推导梯度。
- **修正遮挡缓存**：前向为每个活动图层写入 Alpha 和上层透射率，避免提前终止后反向读取残留缓存。复用原有两块缓存，不增加每像素、每图层的缓存数量，但重叠密集的图片可能需要更多计算。
- **稳定半透明优化**：透明度参数的 Adam 步长缩放为颜色步长的 `1/255`，避免在 `[0,1]` 范围内一次跨过大量中间状态。
- **按残差分配图层**：重定位同时考虑加权 RGB 误差和缺失的 Alpha 覆盖；用局部误差的方向与分布估计椭圆长短轴、角度。选定位置后压低附近优先级，减少多个图层重复堆积；保留五官区域的小尺寸策略。
- **限制破坏性重定位**：默认每轮最多替换约 5% 的图层（小于 20 层时最多 1 层）；局部优化后若误差高于替换前，就恢复替换前参数。仍保存整个过程中的最佳结果。
- **用满迭代预算**：没有图层可重定位以及最后一轮时，原先跳过的局部迭代改为整体精修。全局和局部阶段共用连续衰减的学习率，不在局部阶段重新升到初始值。因此同样的循环数可能比旧版本耗时更长。

`tests/fitting_math_test.cpp` 已通过 648 项多图层数值差分检查（颜色、透明度、几何参数、遮挡和区域权重），以及残差分散覆盖、方向估计、五官尺寸缩放和极小图像检查。这验证了共享的 CPU/CUDA 数学函数，不代表已测出真实图片上的提升百分比。

另提供可选的真实 CUDA 渲染器梯度测试，覆盖整图缓存、分块缓存与完全遮挡后的缓存复用。在安装 CUDA Toolkit 和受支持的 C++ 编译器后运行：

```powershell

cmake --build build-tests/cuda --config Release
ctest --test-dir build-tests/cuda -C Release --output-on-failure
```

后续已补齐开发依赖，上述 GPU 测试及命令行主程序均已编译运行通过。实际画质提升与耗时差异仍需用相同图片、图层数、分辨率和循环数进行 A/B 验证；应同时观察整体、五官区域误差及输出 Alpha。

## 可靠性修复

- 导入前严格验证 JSON 的字段、数组长度、数值类型、有限性、尺寸与 RGBA 范围；占位图层数必须与图形数完全一致，范围为 1–65535（内存计数字段为 16 位，这不是对游戏图层上限的承诺）。不再截断图形或自动清空多余层。
- 定位时检查全部图层、重复指针、可写区域、图形类型、遮罩与有限参数；GUI 与 CLI 都显示抽样信息并要求确认，确认后再全量检查，写入每层前复查所属组的层数和层表指针。任一写入失败立即停止。
- 每层写入前要求所有备份读取完整成功；失败时尝试恢复包括当前失败字段在内的修改，并报告回滚失败。已完成的其他图层不会自动回滚。这些检查降低误写风险，但不能保证游戏运行过程中内存不会变化，也不能代替对应游戏版本的实测。
- GUI 和 CLI 共用加载、格式转换、缩放与优化流程，CLI 的分辨率参数可以降低大图优化尺寸。保留宽高比且不放大小图，原图坐标用于输出。
- 保留输入的连续 Alpha；缩图使用预乘 Alpha，RGB 拟合目标按渲染器相同的线性光混合方式合成。JSON 预览恢复图形透明度，预览尺寸限制为最长边 2048；CLI PNG 预览修正 RGB/BGR 顺序。
- 每个更优的已评估状态在 Adam 更新前保存，覆盖全局、局部迭代和最后一次更新；停止时恢复最佳状态。界面的最终 MSE 对应该已评估状态。
- CUDA 分配/传输/同步失败会中止并向调用方报错；异常退出也会清理资源。JSON 文件打开及最终写入失败会抛出错误，CLI 返回非零，GUI 区分失败、正常完成和停止保存，失败时不会读取旧 JSON 冒充新结果。

当前已编译运行损失、Windows 安全、OpenCV 图像与 CUDA 渲染器测试。安全测试（见 `tests/safety_test.cpp`）只访问测试进程自己的模拟图层内存，不启动或操作游戏。Qt 界面与真实游戏导入仍待验证。

## 人脸、眼睛与嘴部加权

GUI 和 CLI 默认启用五官加权。权重同时用于图形初始化、CUDA 的 RGB 拟合误差与梯度，以及重定位的误差评分。高权重区域使用更小的初始图形和取色窗口，重定位时直接读取局部颜色，减少调色板合并对眼睛和唇部细节的影响。

| 区域 | 默认相对峰值权重 |
| --- | ---: |
| 背景 | 1 |
| 人脸 | 3 |
| 检测到的眼睛 | 12 |
| 微笑模型辅助定位的嘴部 | 10 |
| 人脸内推测的眼睛区域（漏检时） | 7 |
| 人脸内推测的嘴部区域（漏检时） | 6 |

区域边缘平滑衰减，重叠取最大值；权重上限为 15。RGB 损失权重在不透明像素上归一化到均值 1，Alpha 损失保持原样。界面和日志中的 MSE 现在包含五官权重，因此不宜直接与旧版本的普通 MSE 比较。图层总数不因加权增加。

检测使用随项目附带的 OpenCV Haar 模型，构建后自动复制到程序旁的 `assets/haarcascades/`，分发时需保留该目录。也会依次查找 `VINYLIZER_CASCADE_DIR`、工作目录的 `assets/haarcascades/` 和 OpenCV sample 路径。模型来源及原始许可见 [模型说明](assets/haarcascades/README.md)。

眼睛只在人脸上半区检测，嘴部使用下半区的微笑检测结果辅助定位；微笑检测不等同于通用嘴部检测，普通表情使用较弱的位置先验。未检测到人脸时返回中性权重；缺少人脸模型会记录警告。侧脸、大角度旋转和动漫脸仍可能漏检。默认数值可以在 `src/preprocess/facial_saliency.h` 的 `FacialSaliencyConfig` 中调整，或通过 `Preprocessor::set_facial_saliency_config()` 配置。

### 导入逻辑的改动
- 游戏内的占位图形改为**只允许使用基本图形中的矩形或圆形，不允许其他任何图形**，否则禁导入
- 游戏内的层数和软件内的Layer数量必须完全一样，否则禁导入
- 导入时，程序会告诉你检测到了多少个椭圆和多少个矩形，还会随机抽6个图层，将它们的数据放到屏幕上供你审查，你需要确认：
  
  1.椭圆102的数量等于你游戏内使用的圆形占位图层数量，矩形101的数量等于你在游戏内使用的矩形占位图层数量，并且这俩值加起来应该等于总的有效图层数量。
  
  2.RGBA的值符合你在游戏内看到的颜色和透明度。例如，如果你选的是个白色圆，RGBA应该全是255
  
  3.position、scale和angle是正常范围内的值（如果你没乱动图形，position和angle应该全是0.0，scale应该全是1.0）

  4.mask的值是0
  
- 确保这些数据都合规，才确认导入。如果任何数值不符合，千万不要导入！！随便输入点别的什么内容就可取消，或者直接把软件关了。
- 这么做仅仅是为了内存安全，我发现forza-painter的导入代码是采用“评分制”，并且只要求50%的内存数据符合特征，就认为可以导入。但是我在评论区看到有一个老哥反映“显示注入成功，但是游戏内什么都没有”，这恐怕是定位到了内存里的其他位置。毕竟FH6游戏的内存很大，产生错误定位的可能性不是完全没有，这样是有风险的
- 正因如此，vinylizer要求占位图层是椭圆或者矩形，并随机抽样供确认。这只能降低误定位风险，不能保证绝无错写；当前版本的具体检查与局限见上方“可靠性修复”。
